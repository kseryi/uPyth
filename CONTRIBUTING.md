# Contributing / Як долучитись до розробки

Дякуємо за інтерес до uPyth! Цей документ описує, як запропонувати зміну
— від виправлення одруківки до нового блоку чи модуля.

Репозиторій: https://github.com/kseryi/uPyth

## Швидкий старт

1. Форкніть репозиторій і склонуйте свій форк.
2. Встановіть залежності для розробки (потрібні лише для тестів/лінту —
   сам проєкт запускається відкриттям `index.htm` у браузері, без збірки):
   ```bash
   npm install
   ```
3. Перед тим як відкривати Pull Request, локально прогоніть:
   ```bash
   npm test        # юніт-тести (tests/*.test.js)
   npm run lint     # ESLint (eslint.config.js)
   ```
   Обидві команди мають завершуватись без помилок — це ж саме перевіряє
   CI (`.github/workflows/ci.yml`) автоматично на кожен Pull Request.
4. Опишіть зміну в `CHANGELOG.md` у розділі поточної розробки (стиль —
   дивіться попередні записи: короткий заголовок + список змін по
   пунктах, із поясненням "навіщо", а не лише "що").

## Що можна пропонувати

- Виправлення багів.
- Нові блоки для існуючих модулів (Turtle/Tkinter/Pico) — див. окрему
  детальну інструкцію [`HOW_TO_ADD_BLOCKS.md`](HOW_TO_ADD_BLOCKS.md).
- Новий модуль розширення — там само описано мінімальний контракт
  (`registerExtension`, дескриптор модуля).
- Нову мову інтерфейсу — див. коментар на початку `js/languages.js`:
  скопіювати `js/locales/en.js`, перекласти значення (ключі не чіпати),
  підключити один `<script>`-тег в `index.htm`.
- Новий приклад/урок — додайте `.xml`-файл у `lessons/examples/` і
  зареєструйте його в `js/lessons.js`.

## Стиль коду

- Проєкт навмисно без збірки й без фреймворків — чистий ES2017+,
  `<script>`-теги в `index.htm`, спільний глобальний простір імен між
  файлами `src/core/*.js`.
- ESLint-конфігурація (`eslint.config.js`) — орієнтир по стилю; PR, що
  не проходить `npm run lint`, не буде змерджено, поки не виправлено.
- Коментарі в коді пишуться українською — так само, як і в решті
  проєкту (частина авторської практики: коментар пояснює "чому", а не
  повторює те, що й так видно з коду).

## Pull Request

- Один PR — одна логічна зміна (простіше рев'ювати).
- В описі PR коротко: що зроблено, чому, як перевірити вручну (якщо
  зміна не покрита тестами).
- Якщо PR змінює поведінку блоку, який генерує Python-код — обов'язково
  додайте/оновіть тест у `tests/generator.test.js`.

## Питання

Якщо щось незрозуміло — відкрийте
[Issue](https://github.com/kseryi/uPyth/issues) з описом питання,
перш ніж витрачати час на PR, що може піти в неправильному напрямку.
